# Corporation Automation Design & Feasibility

**Target** — Bitburner 3.0.1, Netscript 2.0, one long-running `corp.js` on `home`. The manager owns Corporation decisions from formation through public operation. Daemon or Autopilot can supervise it using the same launch contract.

**Feasibility** — The 3.0.1 API exposes enough state and actions for the full lifecycle in supported BitNodes. The deployment gates are Corporation access, startup cash outside BN3, and enough home RAM to run the combined script. The strategy below uses Agriculture for initial cash flow, adds Tobacco for product growth, and makes Chemical optional. The spending, pricing, and investment parameters are starting points for in-game tuning. [Tagged Corporation API](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/markdown/bitburner.corporation.md) · [Creation checks](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/helpers.ts#L30-L51)

## 2. Configuration and ownership

Keep one `CONFIG` at the top of `corp.js`. Suggested defaults are starting values to validate on a 3.0.1 save.

| Group | Initial policy |
| --- | --- |
| Startup | Corporation name for a fresh start, `auto` funding, $150b player cash threshold for self-funding, and optional additional player cash reserve. Default to `manage` mode. |
| Divisions | Agriculture in Sector-12 first, then use round 1 for a nine-seat Agriculture satellite in Aevum. The package is $18.25b, including a working-cash buffer. Add Tobacco after round 2 when its $35b launch package fits. Use one configured Tobacco development city, Sector-12 by default. Add Chemical only when the supply chain saves more than its ongoing costs and enough managed locations can use its output. |
| Offices and warehouses | Start with the existing three-seat Agriculture office. Assign one Operations, one Engineer, and one Business. Grow the starter office toward nine seats after the budget permits, using an Operations/Engineer/Business/Management/Research & Development weight mix of 2/2/1/1/1 as a configurable starting point. Use heavier Engineering, Management, and Business weights in the Tobacco development office, with an explicit R&D allocation. Configure Research & Development shares as offices grow. Start with an 80% warehouse occupancy ceiling and a 35% boost-material space target, subordinate to operating space. Set city and office size ceilings per stage. |
| Treasury | Keep the greatest of $5b, three cycles of operating expenses, and three game days of settled net burn. Quote and budget committed discretionary purchases above that reserve. Put up to 15% of spendable cash per cycle into discretionary growth initially. On a tight budget use the reserve for essential operations, with expansion and dividends paused. |
| Funding and IPO | Define four round rules with minimum proceeds, the next funded expansion package, and a preference for a higher offer. Sample after `START`. Default to an IPO after round 4, issuing zero shares. Allow a configured earlier IPO when private funding is abandoned deliberately. |
| Pricing and dividends | Set a bounded price multiplier range and step size, stock pressure thresholds, and hysteresis. Default dividends to 0% for compounding. An optional steady-state payout starts with a configurable 10% ceiling once sustained operating profits and the reinvestment reserve are in place. |
| Integration | Canonical script path, one supervisor, launch backoff, status interval, and explicit adoption aliases. Emergency configuration includes a protected division list and an empty list of divisions eligible for sale. |

Identify managed divisions by explicit name or configured alias and validate each against `getDivision().industry`. A name/type collision is a configuration error for that division. An existing division of the desired type can be adopted through an alias. An optional discovery rule may adopt a sole unambiguous match. Leave ambiguous and unlisted divisions outside the manager’s mutation scope while including their contribution in company-wide cash flow. Within adopted divisions, reconcile configured cities, products, and orders, including clearing stale purchase rates for materials the strategy now owns. Three office seats and the initial warehouse in Sector-12 are part of a new division. [Division initialization](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Division.ts#L87-L116) · [Industry costs and recipes](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/data/IndustryData.ts)


### Script layout

```text
daemon.js or autopilot.js
  └─ exec corp.js on home (one instance, one thread)
       ├─ main, phase scheduler, API guards, live-state reconciliation
       ├─ setup, finances, offices, warehouses
       ├─ materials, products, research, upgrades, boosts
       └─ logging and heartbeat
```

The modules are functions in one script. `setup` handles formation and initial facilities. `finances` owns offers, equity, and dividends. `offices` and `warehouses` reconcile facilities and upkeep. `materials` owns buy, sale, and export orders. `products` owns the development queue. `research` evaluates known prerequisites and research-point reserves. `upgrades` ranks levelable purchases. `boosts` proposes boost inventories and tracks advertising and valuation for the finance plan. The scheduler serializes all writes. Repeated references to the same API call are charged once per script by the static RAM calculation, so function boundaries can share calls. Splitting the modules into separate resident scripts would duplicate overlapping API costs and introduce extra coordination. [Netscript RAM calculation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Netscript/RamCostGenerator.ts)

## 3. Lifecycle and investment

Recompute the lifecycle stage on each planning pass from the live snapshot. A public corporation always selects `STEADY`. For a private corporation, the first matching row wins. Corporate market phases and the emergency override are evaluated separately, so a funding opportunity can recur after expansion.

| Stage | Live detection | Primary action |
| --- | --- | --- |
| `NO_CORP` | `hasCorporation()` is false. | Check eligibility and wait for funding or create. |
| `BOOTSTRAP` | Private, with the starter operating package incomplete. | Fund the starter infrastructure, staff it, and establish purchase and sale orders. |
| `IPO` | Private, configured private funding sequence complete or abandoned, and IPO gates pass. | Verify shares and go public. |
| `INVEST` | Private, a round is available, its acceptance gates pass, and no cash-funded buildout has priority. | Accept and re-read the round before spending. |
| `EXPAND` | Private, a cash-funded buildout fits above the reserve or a previously funded buildout is pending. | Launch or grow the division and collect a fresh offer window after it records sales. |
| `GROW` | Private and operating, with no higher-priority action ready. | Maintain cash flow, expand within budget, and improve offers. |
| `STEADY` | `getCorporation().public` is true. | Maintain operations, develop and replace products, reinvest, and manage dividends. |

An adopted corporation that already meets a configured equivalent starter milestone can skip `BOOTSTRAP`. Once public, `STEADY` takes priority over the private stages even when chosen divisions or upgrade targets still need work.


1. **Create or adopt.** Start with `hasCorporation()`. If there is a corporation, adopt it and infer progress from `public`, the offer round, and existing divisions. Otherwise query `canCreateCorporation(selfFund)` and compare its result with `Success`. In auto mode, try the seed eligibility check first. A `UseSeedMoneyOutsideBN3` result selects the self-funded check. Once the self-funded check succeeds, wait until personal cash covers $150b plus the configured reserve. BN3 can use seed funding. BN4 and BN10 need access from SF3 and personal cash. `NoSf3OrDisabled` and `DisabledBySoftCap` suspend formation with a named status. The game blocks formation below a Corporation softcap of 0.15. In BN10 the valuation multiplier is 0.5, so offer targets calibrated in BN3 may be too high. Recheck existence after calling `createCorporation`, even if its return or error is unexpected. [Tagged creation implementation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Actions.ts#L33-L67) · [BitNode multipliers](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/BitNode/BitNode.tsx)
2. **Bootstrap Agriculture with manual supply.** A new corporation starts with $150b of corporate funds. Agriculture costs $40b, Office API and Warehouse API cost $50b each, and the original city has a warehouse. This leaves $10b before operating costs. Treat the three purchases as one budgeted package but reconcile one action at a time so a restart can finish it. Hire and staff the initial office, buy Water and Chemicals with bounded rates, and sell Food and Plants. Smart Supply ($25b) and Export ($20b) are beyond the initial budget. Opening a second city would leave only $1b before supplies, below the default reserve. Once cash flow is healthy, buy Smart Supply if it fits and expand one complete office-and-warehouse package at a time. A new non-home city costs $4b for its office and $5b for its initial warehouse, before staffing, operating supplies, and upgrades. [Starting funds](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Corporation.ts#L33-L67) · [Unlock prices](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/data/CorporationUnlocks.ts) · [Facility costs](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/data/Constants.ts#L44-L72)
3. **Take private rounds 1–4.** Use `getInvestmentOffer()` as the authoritative round and proceeds. Require a finite, positive offer and readiness for the next stage. Accept when the preferred target is met or after a configurable observation window, provided the offer still meets the hard floor and funds the next package after reserves. A starting hard floor is the incremental cash required for the next package and reserves after accounting for existing cash. Round 1 requires an offer of at least $12b and coverage of the package and reserve from cash, the offer, and five settlements of projected operating profit. Rounds 2–4 require actual cash coverage and compare the live offer with the recent modeled quote for that round. The proposed 10× growth targets can be optional per-round tuning. Use a configured valuation baseline per round if enabled, since the API gives the live offer and round but does not expose the valuation at which the last offer was accepted. The game valuation averages up to ten observations, so start with ten observed `START` updates after a major expansion before judging a plateau. Track that window in memory and rebuild it after restart. Keep operating and allow affordable improvements if offers stay below the floor. Re-read immediately before acceptance and verify the round advanced after it. An early IPO ends eligibility for remaining private rounds. [Offer and valuation implementation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Corporation.ts#L198-L232) · [Round and IPO mutations](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Actions.ts#L144-L208)
4. **Scale and go public.** Use round 1 for the second Agriculture city. The $18.25b Aevum package is the first Round 1 coverage target while the satellite is still pending. Require two consecutive profitable nine-seat cycles with rising funds. After Tobacco exists, require three consecutive settled observations with measurable Tobacco sales. Use round 2 for Tobacco staffing, advertising, and the first product line. Use rounds 3–4 for proven capacity, sales bottlenecks, and replacement products. Gate IPO on adequate liquidity and a sustained operating business. Recheck `public`, `numShares`, and the configured whole-share quantity before `goPublic`. After IPO, set dividends in the API’s 0–1 range and reduce to zero if liquidity or operating results deteriorate. Corporation operating cash, player cash, and player dividend earnings are separate budget inputs. For optional corporate fundraising, `issueNewShares` credits company funds after IPO. Require `issueNewSharesCooldown <= 0`, a configured minimum share price, a concrete funding need and ownership floor, and a share quantity in 10m increments within the game limit. Verify the increase in total shares. Optional CEO sales require a ready `shareSaleCooldown` and enough CEO-owned shares. Buybacks require sufficient player cash and publicly issued shares. Both settle in the player wallet. Keep such trades disabled by default. [New share issuance](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Actions.ts#L161-L187) · [Issuance limits](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/helpers.ts#L118-L130) · [Personal share transactions](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Actions.ts#L367-L393) [Corporation financial statement](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Documentation/doc/en/advanced/corporation/financial-statement.md)

## 4. Cycle scheduling and reconciliation

The loop sleeps with `await ns.sleep()` on every pass, including startup and error paths. Use a short yield during active phase handling and a capped backoff while waiting for access or cash. Once a corporation exists, use a single guarded `await ns.corporation.nextUpdate()` to synchronize. On launch, inspect and repair time-sensitive orders for the currently upcoming phase. On subsequent updates, read a fresh `nextState` before writing. Its order is `START → PURCHASE → PRODUCTION → EXPORT → SALE`. Bonus time can shorten intervals. Keep work bounded and defer operations whose required phase has passed. The completed state is useful for telemetry and triggers such as freshly settled profits. [Phase definitions](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/data/Constants.ts#L24-L54) · [Update timing](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/markdown/bitburner.corporation.nextupdate.md)

| Upcoming phase or observation | Work |
| --- | --- |
| Before `START` | Queue staffing changes for offices that need them. Apply any required dividend reduction before settlement when possible. |
| Just after completed `START` | Sample settled financials and offers. Refresh the discretionary budget. Reconcile unlocks, strategic purchases, research, product starts, and financing within the remaining phase window. |
| Before `PURCHASE` | Set persistent purchase rates and Smart Supply options. Give inputs first claim on cash and warehouse space. |
| Before `PRODUCTION` | Check inputs and headroom. Apply a temporary production cap where stocks or free space indicate a bottleneck and remove it after recovery. |
| Before `EXPORT` | Reconcile configured routes against live exports and current stocks. |
| Before `SALE` | Set and maintain city-level sale orders. Sample sell-through after a completed `SALE` for the next price decision. |

Wrap all Netscript calls, including reads and waits, with operation context and API-specific success handling. The wrapper distinguishes a missing resource, an unmet prerequisite, a `false` result, a successful void call, and an exception. A failed read leaves that entity unknown and blocks dependent writes. For a paid or irreversible action, refresh its prerequisite, quoted cost, funds, and desired-state predicate immediately before submitting it. Verify the actual postcondition afterward. If verification fails, defer the action and replan from fresh state. Use explicit API references inside wrapped calls so Bitburner can account for their RAM normally.

Use `hasUnlock → getUnlockCost → purchaseUnlock → hasUnlock` for missing features when the budget permits. `hasWarehouse` itself needs Warehouse API. Office reads, hiring, advertising, and research need Office API. Smart Supply and Export require Warehouse API in addition to their own unlock. A blocked optional feature degrades to the manual equivalent where available. Use capped backoff on repeated failures and log the prerequisite, location, and price when it prevents progress. [Tagged method access checks and return values](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/NetscriptFunctions/Corporation.ts)

## 5. Operating policy

- **Staffing and upkeep.** Read occupancy before hiring and fill only the planned seats. Choose integer job targets with deterministic remainder allocation. `getOffice().employeeJobs` reports applied jobs. When a rebalance is needed and queued counts may differ, reduce assignable roles to zero before filling the target counts in one synchronous batch. Freeing roles creates unassigned capacity automatically. Verify after the next `START` and repair a partial update there. Buy tea and hold bounded parties only below configured energy and morale triggers, priced per employee. [Office job implementation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/OfficeSpace.ts#L53-L71) · [Assignment validation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/NetscriptFunctions/Corporation.ts#L508-L540)
- **Inputs and boost materials.** Read recipes from `getIndustryData` and sizes from `getMaterialData`. Manual supply targets one cycle of forecast consumption plus a small buffer, with an explicit initial seed quantity when production data is zero. Convert a quantity deficit into a per-second `buyMaterial` rate using `getConstants().secondsPerMarketCycle`. Cap the sum of all proposed buys by remaining cash and shared free volume after reserving room for imports and output. Zero persistent rates when targets are reached or funds tighten. Buy rates can survive an abrupt stop and continue executing until the manager restarts, so prefer a budgeted one-time `bulkPurchase` for initial seeding or recovery when ongoing rates are unnecessary. With Smart Supply active, set the input policy to `leftovers` initially, including in import-fed warehouses so stock on hand offsets purchases. If Smart Supply stalls with zero forecast production or needs to be constrained for cash or space, disable it temporarily, clear its retained input rates, and use the bounded manual input plan until production is stable. Apply separate rate and spend limits to the four boost materials. Split boost space among positive industry factors and revise the mix only when utilization and returns justify it. Allow a config-gated Agriculture preset of 1:1:1:5 unit weights for Hardware, Robots, AI Cores, and Real Estate, with total quantities scaled to the combined space and cash budgets. [Buy and Smart Supply implementation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Division.ts#L490-L565)
- **Exports and warehouse pressure.** Start with Plants from Agriculture to Tobacco in shared cities. Optionally send Plants to Chemical and Chemicals back to Agriculture if both sides have buffers. Market purchases cover any shortfall. Compute bounded numeric export rates from destination shortfall, exporter surplus, free volume, and the duration of a cycle. Allocate among destinations before setting routes. Inspect `getMaterial().exports`, preserve matching routes, and cancel then recreate changed managed routes because duplicate destinations are rejected. Verify the replacement and repair on restart if interrupted. With sustained congestion, stop boost buys and clear surplus sale inventory. Consider storage expansion above a configurable sustained utilization threshold such as 90%, with a configurable minimum cash-to-upgrade-cost ratio such as 3×, once output is selling and the reserve is covered. [Export actions](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Actions.ts#L543-L599) · [Supply chain documentation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Documentation/doc/en/advanced/corporation/industry-supply-chain.md)
- **Sales and product rotation.** Set material and completed product orders in each city. Start with `MAX` and an `MP`-based price. For inputs reserved for internal use, cap sell quantity by surplus. Raise the price gradually on repeated sell-through with low carryover and lower it on persistent stock buildup. Reconstruct the last price from live sale settings. Product `MP` is production cost, so target a margin above that cost once demand supports it. Research Hi-Tech R&D Laboratory, then Market-TA.I and Market-TA.II when points permit. Enable TA.II once researched and let it price the configured sale quantities. Enable material TA by city and product TA by product. Maintain one product in development per managed product division with funded design and marketing in its configured development city. Offer capped 5%/5% design and marketing targets based on spendable corporate cash, constrained by the remaining combined budget. Treat `developmentProgress >= 100` as completion. Use `getDivision().maxProducts` for slots. At capacity, protect the best seller and retain at least one selling product. Replace a persistently weak, completed product only after reserving both replacement budgets. If interrupted after discontinuing, fill the vacant slot on the next eligible pass. [Product and market API](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/NetscriptFunctions/Corporation.ts#L254-L279) · [Sale pricing and TA behavior](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Division.ts#L294-L388)
- **Scaling.** Rank purchases by the observed bottleneck. Compare warehouse levels with Smart Storage for space, offices and Smart Factories for capacity where inputs and sell-through are healthy, and Business staffing, AdVerts, or ABC SalesBots for weak sell-through. Evaluate Wilson Analytics once advertising spend is substantial. Quote each incremental purchase and reassess afterward. An optional conservative upgrade preset limits discretionary upgrades to one tenth of spendable cash per purchase. Distinguish research points from cash. Keep a research-point reserve around product development, since the game uses the division’s unspent research when a product finishes. Use the configured prerequisite order and `hasResearched` plus `getResearchCost` for live checks. Apply capacity research once product slots constrain profitable growth. [Tagged upgrade data](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/data/CorporationUpgrades.ts) · [Base research tree](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/data/BaseResearchTree.ts)

## 6. Emergency behavior

Normal mode automatically enters cash preservation when reserves or operating results breach the configured thresholds. Shutdown contract: stop spending-side orders and keep earning-side orders. At startup, bounded stop, and `atExit`, sweep live `getMaterial().buyAmount` for the strategy-owned inputs and boost materials in every city of explicitly managed divisions, including adoption aliases. Clear those purchase rates and disable Smart Supply; verify the changes and continue cleaning other locations if one call fails. Retry incomplete startup cleanup before normal purchasing. Preserve sale orders, Market-TA flags, and export routes so existing stock can earn cash. Unlisted divisions stay outside the sweep. Suspend discretionary spending and product replacement, zero dividends when public, reduce new purchases to essentials, and sell surplus stock. With negative funds, clear managed buy rates, disable managed Smart Supply, and restrict operations to sales and available financing until cash recovers. Resume normal spending after several healthy settled cycles. If cash runs out, log the recovery options still available to this corporation, such as an eligible private offer, configured public equity issuance, or an explicitly configured division sale. Any CEO share sale yields personal cash.

An explicit liquidation mode may sell only allowlisted, unprotected divisions. Freeze their new spending, prepare replacement supply for surviving consumers, and check the name, industry, and current existence before each sale. Verify that the division disappeared and preserve liquidation mode across restarts through the launch configuration, preventing recreation. The game removes incoming routes referencing the sold division and credits the recoupable value to corporate funds. Read back both funds and routes. [Division sale implementation](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Corporation/Actions.ts#L98-L119)

## 7. Daemon and Autopilot integration

- Install `corp.js` on `home`. Choose daemon or Autopilot as supervisor. Check for the canonical filename on `home` across argument variants, launch one thread with stable arguments via `ns.exec`, and verify the PID. `ns.spawn` terminates the calling script, so use `ns.exec` to keep the supervisor running. Add an entry check in the manager so only the oldest matching PID can write if two launches occur. The supervisor checks measured `getScriptRam` against free home RAM and backs off if a launch fails. Corporation getters typically cost 10 GB each and mutations 20 GB each, so a full combined script can require several hundred GB even while waiting to form a corporation. The productivity audit used a 475 GB override. The installed 3.0.1 RAM calculator reports 858.40 GB of static RAM with the M6 finance and emergency paths. The Tobacco lifecycle build measured 778.40 GB. For supervisor wiring, measure the exact script each milestone and reserve the current result plus configured headroom. Keep the existing home RAM purchase task available so the daemon can grow into that reservation as player cash allows. [Tagged RAM costs](https://github.com/bitburner-official/bitburner-src/blob/v3.0.1/src/Netscript/RamCostGenerator.ts#L466-L532)
- The integration target is `NOTsave/bitburne_scripts_ada`, a fork of `alainbryden/bitburner-scripts`. On November 15, 2026, its `main` was 17 commits ahead of upstream `main`. Add `corp.js` at the fork root alongside `gangs.js` and the other managers. The current daemon and Autopilot have no Corporation manager or dividend controller. [Fork comparison](https://github.com/alainbryden/bitburner-scripts/compare/main...NOTsave:bitburne_scripts_ada:main) · [Daemon manager list](https://github.com/NOTsave/bitburne_scripts_ada/blob/main/daemon.js#L352-L385) · [Autopilot BitNode policy](https://github.com/NOTsave/bitburne_scripts_ada/blob/main/autopilot.js#L75-L81)
- Add an opt-in `--corp` flag to `daemon.js`. Use the daemon’s home-only readiness and `ns.exec` pattern, with a recurring check for a missing PID so the supervisor can restart the manager after a crash. The existing one-shot helper list stops checking a helper once it has launched. For Autopilot-managed runs, opt in through the daemon’s existing `daemon.js.config.txt` configuration by setting `"corp": true`. Autopilot can use its existing daemon launch path while `corp.js` owns Corporation decisions. [Daemon readiness check](https://github.com/NOTsave/bitburne_scripts_ada/blob/main/daemon.js#L725-L780) · [One-shot scheduling](https://github.com/NOTsave/bitburne_scripts_ada/blob/main/daemon.js#L585-L595) · [Config loading](https://github.com/NOTsave/bitburne_scripts_ada/blob/main/helpers.js#L814-L859) · [Autopilot daemon launch](https://github.com/NOTsave/bitburne_scripts_ada/blob/main/autopilot.js#L659-L674)
- Report transitions via `ns.print` and send a throttled `ns.tprint` summary every configurable number of cycles. Overwrite a single JSON line on `home` at a configured status path such as `/Temp/corp-status.txt` using `ns.write`. Include a wall-clock timestamp, PID, lifecycle stage, upcoming phase, funds, operating rate, reserve, next offer, and current blocker. Refresh on stage changes and at least every 15 seconds of active play, including while waiting for creation. The supervisor can read it with `ns.read`, discard stale or mismatched-PID data, and restart a missing process with backoff. A stale file alone is diagnostic, since game suspension can stall heartbeats. When supervision itself restarts after an augmentation or BitNode reset, it should recheck the running PID, access, and RAM before relaunching. Keep telemetry outside Corporation decisions. Reconstruct purchase, hiring, research, and funding decisions from live game state after every restart. Rolling samples may be rebuilt, temporarily delaying price changes or investment decisions.

## 8. Acceptance checks for implementation

| Scenario | Expected result |
| --- | --- |
| Fresh BN3 and eligible BN4/BN10 | Seed in BN3, wait for self-funding elsewhere, and reach first Agriculture sales with manual inputs inside the $150b corporate budget. Blocked Corporation access produces a stable status without repeated creation errors. |
| Adopt existing corporation | Preserve unlisted divisions. Reconstruct partial offices, warehouses, staffing, old buy rates, existing routes, the next funding round, and current IPO status. |
| Restart during a mutation | Retry after one unlock, one staffing reduction, export cancellation, product retirement, accepted round, and IPO. Each converges without repeating a completed irreversible action or buying beyond target. |
| Accelerated phases or insufficient funds | Keep observing updates, avoid stale phase writes, cap purchase commitments, and clear managed orders that would continue draining funds. |
| Product and liquidity changes | Progress from manual pricing to TA.II, recover from saturation and input shortages, rotate products with a live seller, and reduce dividends when operating cash tightens. |
| Supervisor and liquidation | A competing launch exits without writing and a low-RAM launch backs off. Verify daemon opt-in both directly and through Autopilot’s daemon launch, and that the daemon restarts a missing manager without starting a duplicate. Interrupted liquidation preserves protected assets and keeps sold divisions absent. |


## 9. Implementation milestones

1. Build the loop, live stage detection, dry-run planner, and heartbeat. Observe a full market cycle with Corporation mutations disabled.
